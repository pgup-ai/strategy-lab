# R10a — persist the why-layer on the path that cannot recompute it

**A design plan, not a pre-registration.** R7–R7d were research phases and were
pre-registered because they produce numbers a protocol has to bind in advance.
This one produces a schema and a diff, so it declares a **design** and a
**gate** instead. Nothing here selects anything or publishes a figure.

**Charter:** [docs/research/2026-08-03-market-dynamics-engine.md](../research/2026-08-03-market-dynamics-engine.md),
phase R10, which **M31** made the program's main line: the state-machine
sequence ended on the finding that the estimator works and the book does not, so
execution is the open problem and this is the phase that owns it.

---

## The finding that shapes this, and it inverts the obvious plan

The 2026-08-05 census said the `signals` table records *configuration*, not
*reasons*. That is still true, and `runner._features`' own docstring says so:

> Stringifying is what guarantees the payload is JSON-serialisable … but it is
> lossy: `True` comes back as `"True"` and `200` as `"200"`. **Read these as
> labels, not as values to compute or branch on.**

But the obvious remedy — "persist the reasons" — is **half wrong**, because the
research path already has them and is right not to store them.
`api/analysis.py` computes a `WhyLayer` per bar, and its docstring is the
argument against persisting it:

> Both existing paths compute this and throw it away. It is returned rather than
> persisted: **no schema change, no migration, and no second copy of the research
> record to fall out of step with the first.**

That reasoning holds and this plan does not overturn it. Recomputing the reasons
for a stored frame costs **19 ms** (Q6), the inputs are immutable candles, and a
stored copy of a deterministic function of stored data is a second record to
drift.

**What is genuinely unrecomputable is what a *live* run saw at the moment it
decided.** Funding that had not settled yet, a feed gap, a bar that arrived late,
a revision — none of it is recoverable from `market_candles` afterwards. So:

> **The research path keeps recomputing. The event path persists. The gate is the
> diff between them.**

That is R10's own gate — *"research and live code paths produce identical
output"* — made checkable per bar rather than per signal.

---

## What gets built

### 1. A table for per-bar reasons, not a widened `signals`

`signals` is the wrong home and Q3's answer does not extend here. It is keyed to
**events**: ~73 rows for the R5 test half against **15,118** bars. It is
append-only through two triggers because it is a record of decisions, and reasons
are the *inputs* to a decision rather than one.

`bar_reasons` (name to settle in review), one row per `(run_id, instrument,
strategy, bar)`, carrying the state label and the feature values the machine
actually read. Keyed by `run_id` like `signals`, so a second replay adds a run
rather than mutating one — the same reason `signals` is append-only, and the same
consequence: replaying a range twice is expected to double the rows.

**Written by the event path only.** `backtest`, `sweep` and the browser write
nothing, and the browser keeps recomputing.

### 2. The runner extracts it by the introspection that already exists

`api/analysis._why_layer` finds `feature_frame` and `machine` by `getattr`,
deliberately rather than by matching a list of state machines. `StrategyRunner`
uses the **same** convention — one rule for "can this strategy explain itself",
not two — so a strategy that grows a `feature_frame` later is explained on both
paths without anyone editing either.

The runner already calls `generate_signals` once per closed bar over an expanding
buffer and reads the last row. The reasons come off the same call's last row.

### 3. Every bar, not only signal bars

The question the dashboard exists to answer is at least as often *"why did it
**not** trade here"* as *"why did it trade"*. Reasons on decision bars alone
cannot answer the first, and it is the one that a state machine spending 82.9% of
its bars in `COMPRESSION` (§9.6) mostly needs.

## The gate

**A bar-by-bar diff of stored-live reasons against browser-recomputed reasons,
over the same range, for the same strategy.** Equal on every bar for every
feature and the state, or the two paths are not producing identical output and
the difference is now *named* rather than suspected.

**It is expected to fail immediately, and that failure is the first
deliverable.** Census item (a): `Bar` has no funding field, so replay runs both
state machines crowding-neutral while a backtest measures `crowding` (M20,
measured +15.45% / +0.896 against +16.44% / +0.801 on BTC's trained cell). So the
diff should show **`crowding` differing on every bar and the other four
agreeing**, and the state differing wherever that changed a transition.

That is the point of building it. The six census items are currently a prose list;
after this they are a diff with a row count. An item that turns out to disagree on
bars nobody predicted is worth more than the four that behave.

**Declared before running it**, so the result cannot be read backwards:

| Diff shows | Reading |
|---|---|
| `crowding` differs, other four agree, state differs only where crowding moved a transition | (a) is the whole of the live/research gap for this strategy, and closing it is the funding-through-`Bar` phase CLAUDE.md already describes |
| Anything else differs | an unenumerated gap exists — it is found here rather than in production, and it is the phase's real result |
| Nothing differs | replay is not exercising the path the diff is meant to compare; suspect the harness before celebrating |

The third row exists because the determinism suite is already blind to (a) —
census item (e) — by comparing crowding-neutral against crowding-neutral on
`synthetic_ohlcv`. A green diff for the same reason would be the same failure
wearing a different hat.

## What this deliberately does not do

- **No live feed.** `ReplayFeed` satisfies `MarketDataFeed`; a live one changes
  what fills the socket, not this schema.
- **No funding through `Bar`.** That is the phase CLAUDE.md calls "a phase and
  not a patch" — carrying it through `Bar`, `BarBuffer`, the feed and the storage
  schema. This plan *measures* the gap so that phase can be scoped from a number.
- **No exit modes in replay** (Phase 1b), **no `TargetExposure` on the event
  path** (census (d)). Both stay open and both become measurable once reasons are
  stored.
- **No change to any published figure.** No strategy, policy, feature or engine
  file is touched; the research path's behaviour is byte-identical, and that is a
  test.

---

## Success, stated as checks rather than as prose

1. `state_machine_v1` replayed over a stored perp range writes one reasons row
   per bar, and the count equals the bar count.
2. The diff against the browser's recomputed `WhyLayer` runs, and its
   disagreements are reported per feature with a row count.
3. **Every published figure is unchanged** — the byte-identity control R7b and
   R7d used, against a clean `main` worktree.
4. A strategy with no `feature_frame` (the four originals, `donchian`) writes
   **no** reasons rows rather than empty ones — an absent explanation and an
   empty one are different claims, the same rule `_why_layer` already follows.
5. The append-only and `run_id` semantics match `signals`, including that a
   second replay of one range adds a second run's rows.

## Then, and not before

The dashboard reads this. Per-bar state and feature values behind every signal,
switchable by strategy, is the "far more metadata per bar" half of the product
vision — and with the diff in place it is reading a record whose agreement with
the research path is measured rather than assumed.
